# File guide: what every file does

This is a tour of the repository for someone new to this kind of project. Read it top to
bottom once, then use it as a map. For the *ideas* behind the code (caching, circuit
breakers…), see [CONCEPTS.md](CONCEPTS.md).

## The big picture in one paragraph

Four small programs run together. The **supplier** pretends to be a slow hotel-inventory
company. The **MCP server** is what Claude talks to: it receives tool calls like
"search hotels in Goa", answers from the **Redis** cache when it can, and only asks the
supplier when it must, protecting the supplier with rate limits, a circuit breaker and load
shedding. The **dashboard** reads counters from Redis and draws live charts. **Docker
Compose** starts all of them with one command.

## Following one request

When Claude asks *"hotels in Goa this weekend"*, the code runs in this order:

1. `mcp_server/server.py` → `search_hotels()` receives the call and validates the input
   (`validation.py`).
2. `server.py` → `run_tool()` counts the request (`metrics.py`) and checks the client's rate
   limit (`ratelimit.py`).
3. `search.py` → `HotelService.search()` looks in the cache (`cache.py`).
   - **Hit:** return immediately.
   - **Miss:** `SingleFlight` makes sure only one identical request goes to the supplier.
     `_call_supplier()` asks the circuit breaker (`breaker.py`) and the load shedder
     (`shedding.py`) for permission, then calls `SupplierClient` → `supplier/app.py`.
   - **Supplier failed:** serve the last-known-good copy with `stale: true`.
4. The result travels back to Claude as JSON.

## `supplier/`: the fake hotel company (port 8001)

| File | Purpose |
|---|---|
| `supplier/app.py` | A FastAPI web app imitating a real supplier API. `GET /hotels/search`, `GET /hotels/{id}`, `GET /hotels/{id}/price`. Every call waits 300–800 ms (like a real slow upstream). Prices change with dates: weekends +25 %, December +35 %, Christmas week +70 %, plus ±3 % noise. Admin endpoints `/admin/failure-rate`, `/admin/down`, `/admin/up` let the demo break it on purpose. It counts every search/price call as a "look" in Redis. |
| `supplier/data/hotels.json` | 60 made-up hotels (10 per city) with name, area, stars, rating, base price, amenities. Generated by `scripts/gen_hotels.py`. |
| `supplier/__init__.py` | Empty; marks the folder as a Python package so it can be imported. |

## `mcp_server/`: the MCP server Claude talks to (port 8000 or stdio)

| File | Purpose |
|---|---|
| `server.py` | **The entry point.** Defines the four MCP tools Claude sees (`search_hotels`, `get_hotel_details`, `check_live_price`, `book_hotel`). Their descriptions matter: the model reads them to decide which tool to call. `run_tool()` wraps every call: counts it, applies the rate limit, and turns internal errors into friendly messages. `main()` starts the server over **stdio** (for Claude Desktop/Code) or **HTTP** (`--http`, several worker processes). It also sets up plain logging (see the comment there for why). |
| `search.py` | **The business logic** (`HotelService`). Decides cache vs. supplier, applies coalescing, breaker and shedding around every supplier call, falls back to stale data, adds the `source`/`stale`/`notice` fields, and builds the mock booking confirmation. `SupplierClient` is the HTTP client that actually calls the supplier. |
| `cache.py` | `RedisCache` stores each answer twice: a *fresh* copy (10 min for searches, 24 h for details) and a *last-known-good* copy (7 days) used only when the supplier fails. `SingleFlight` is the request coalescing: identical concurrent requests share one supplier call. `search_key()` builds the cache key from city + dates + guests + max price. |
| `ratelimit.py` | Token-bucket rate limiter per client, stored in Redis. The check-and-take step is a small Lua script that runs atomically inside Redis, so concurrent requests can't cheat. If Redis is unreachable it lets traffic through ("fail open"). |
| `breaker.py` | The circuit breaker (closed → open → half-open → closed). Its state lives in Redis, so every server process (and the dashboard) sees the same state. Only one "probe" request is allowed through when testing recovery. |
| `shedding.py` | Priority load shedding: limits concurrent supplier calls, reserving the last slots for more valuable work (searches may use 60 %, live price checks 90 %, bookings 100 %). |
| `metrics.py` | Counters in Redis (totals plus one bucket per second for rates). Defines the names of all counters in one place, so the server, supplier and dashboard agree. |
| `config.py` | Reads every setting from environment variables, with defaults. Also lists the supported cities. |
| `validation.py` | Checks tool inputs (dates, city, guests, hotel id) and produces error messages written for the model to read and act on. |
| `redis_client.py` | Creates the Redis connection with a *blocking* connection pool, so under a spike requests wait briefly for a connection instead of crashing. |
| `__init__.py` | Empty package marker. |

## `dashboard/`: live metrics page (port 8002)

| File | Purpose |
|---|---|
| `dashboard/app.py` | Small FastAPI app. `GET /` serves the page; `GET /api/metrics` returns counters, per-second series, cache hit rate, look-to-book ratios and breaker state as JSON; `POST /api/reset` zeroes the counters. |
| `dashboard/index.html` | The page itself: plain HTML + vanilla JavaScript + Chart.js (from a CDN). Polls `/api/metrics` every second. Shows KPI tiles, a traffic chart (MCP requests vs supplier looks), how searches were served (cache hit / coalesced / supplier / stale), the look-to-book comparison, and a table of all counters. Supports dark mode. |
| `dashboard/__init__.py` | Empty package marker. |

## `loadtest/`

| File | Purpose |
|---|---|
| `loadtest/locustfile.py` | The traffic spike for `make spike`, written for [Locust](https://locust.io). Simulated "AI agents" mostly ask the same popular questions (Goa this weekend, Manali in December), sometimes ask unusual dates, check live prices, and occasionally book. Three "noisy bots" hammer one search to trigger the rate limiter. The `Spike` shape ramps from 5 to 500 users in about 20 s. Runs inside Docker. |

## `scripts/`: helper programs

| File | Purpose |
|---|---|
| `scripts/tasks.ps1` | The PowerShell code behind `.\make` on Windows (same targets as the Makefile). |
| `scripts/gen_hotels.py` | Regenerates `supplier/data/hotels.json` (fixed random seed, so the output is always the same). |
| `scripts/smoke.py` | Connects as a real MCP client and calls every tool once, including two calls that should fail politely. Quick "is everything wired up?" check (`make smoke`). |
| `scripts/scenario.py` | Scripted version of the failure story: warm cache → rate limit → supplier down → breaker opens → cached/stale answers → supplier up → recovery (`make scenario`). |

## `tests/`: automated tests (`make test`)

| File | Purpose |
|---|---|
| `tests/conftest.py` | Shared test fixtures: an in-memory fake Redis (`fakeredis`), a `FakeSupplier` that counts calls and can be told to fail, and a ready-made `HotelService`. |
| `tests/test_cache.py` | Coalescing (100 identical searches → 1 supplier call), error and cancellation handling, fresh vs stale copies, cache keys, details caching, live price never cached, booking counter. |
| `tests/test_resilience.py` | Circuit breaker transitions (with a fake clock), single half-open probe, token bucket behaviour, load-shedding priorities, stale fallback when the supplier is down. |
| `tests/__init__.py` | Empty package marker. |
